Тема: Резильєнтність, метрики та Health Checks у мікросервісній архітектурі

Мета: ознайомлення з патернами resilience для підвищення надійності розподілених систем, політиками retry та circuit breaker (Polly через .NET Aspire), створенням власних бізнес-метрик через OpenTelemetry Meter API, налаштуванням health checks для всіх інфраструктурних компонентів, візуалізацією метрик і стану сервісів в Aspire Dashboard.

Програмне забезпечення: ОС Windows/Linux, Visual Studio, Visual Studio Code; .NET 8/9 SDK; Docker Desktop.

Завдання

Розширте мікросервісну платформу з Лаб. 05–06 механізмами resilience та observability: налаштуйте resilience-політики для HTTP- та gRPC-клієнтів Aggregator, graceful degradation для кешу, власні бізнес-метрики та health checks для всіх залежностей.

Компонент Опис
Retry Policy Автоматичне повторення невдалих запитів з експоненційною затримкою для тимчасових збоїв (мережеві проблеми, короткочасна недоступність сервісу).
Circuit Breaker Захист від каскадних відмов: за перевищення порогу збоїв виклики відхиляються одразу (fail-fast), даючи сервісу час відновитися.
Custom Metrics Бізнес-лічильники та вимірювання затримок ключових операцій через OpenTelemetry Meter API: кількість замовлень, тривалість критичних операцій.
Health Checks Ендпоінти стану сервісів, баз, кешу й залежностей; їх використовують оркестратори (перезапуск) і балансувальники (маршрутизація трафіку).
Dashboard Monitoring Централізована візуалізація метрик, traces, логів і стану всіх компонентів в Aspire Dashboard.

Результат роботи:

  • тимчасові збої сервісів поглинаються повторами, а систематичні — розмикають circuit breaker;
  • політики відрізняються для критичних (Каталог) і некритичних (Відгуки) сервісів;
  • недоступність Redis не ламає сервіс — він читає з бази даних;
  • бізнес-операції видно в метриках; кожен сервіс має liveness і readiness endpoints, а Dashboard показує стан усіх ресурсів.

Health checks налаштовуються для SQL Server (Замовлення, Каталог), MongoDB (Відгуки), Redis і gRPC-сервісів, від яких залежить Aggregator. Ці ж endpoints використає Kubernetes у Лаб. 10.

Порядок виконання роботи

Частина 1. Впровадження Resilience Patterns через .NET Aspire (обов’язково)

Налаштувати вбудовані механізми resilience .NET Aspire для підвищення відмовостійкості системи.

1.1. Standard Resilience Handler

Ознайомитися з вбудованими можливостями resilience:

  • шаблон ServiceDefaults уже підключає пакет Microsoft.Extensions.Http.Resilience (на основі Polly) і додає стандартний обробник до всіх HttpClient — це видно в ConfigureHttpClientDefaults з Лаб. 05;
  • Standard Resilience Handler поєднує п’ять стратегій, від зовнішньої до внутрішньої: rate limiter, загальний таймаут, retry, circuit breaker, таймаут однієї спроби;
  • стратегії спрацьовують на HTTP-статуси 5xx, 408, 429 та на винятки HttpRequestException і TimeoutRejectedException;
  • телеметрія resilience-подій автоматично потрапляє в логи й метрики (Частина 1.8);
  • ⚠️ Важливо: окремо встановлювати Polly не потрібно.
Стратегія Значення за замовчуванням
Rate limiter до 1000 одночасних запитів, черга 0
Загальний таймаут 30 с (разом з усіма повторними спробами)
Retry 3 повтори, експоненційна затримка від 2 с, jitter
Circuit breaker розмикається, якщо частка збоїв ≥ 10 % при ≥ 100 запитах за 30 с; розімкнений 5 с
Таймаут спроби 10 с на кожну спробу

Таблиця 2. Стандартні налаштування Standard Resilience Handler (Microsoft Learn).

1.2. Resilience для клієнтів Aggregator

Переконатися, що стандартна resilience діє для HTTP- та gRPC-клієнтів Aggregator:

  • оскільки обробник підключено через ConfigureHttpClientDefaults, він уже діє для typed HttpClient (Лаб. 05) і для gRPC-клієнтів (Лаб. 06), бо ті створюються тією самою фабрикою;
  • не додавайте AddStandardResilienceHandler() до клієнта вдруге — обробники не повинні нашаровуватися. Щоб змінити налаштування для конкретного клієнта, спершу приберіть стандартний (RemoveAllResilienceHandlers), потім додайте власний;
  • Особливість gRPC: gRPC повертає помилки (Unavailable, DeadlineExceeded) як статус у трейлерах відповіді з HTTP 200, тому HTTP-обробник їх не повторює — він спрацьовує лише на мережеві збої та таймаути. Для повторів за gRPC-статусами використовується вбудована retry-політика gRPC-клієнта.

CSHARP

builder.Services.AddGrpcClient<CatalogService.CatalogServiceClient>(o =>
    o.Address = new Uri("https://catalog-api"))
    .ConfigureChannel(channel => channel.ServiceConfig = new ServiceConfig
    {
        MethodConfigs =
        {
            new MethodConfig
            {
                Names = { MethodName.Default },
                RetryPolicy = new RetryPolicy
                {
                    MaxAttempts = 4,
                    InitialBackoff = TimeSpan.FromSeconds(0.5),
                    MaxBackoff = TimeSpan.FromSeconds(4),
                    BackoffMultiplier = 2,
                    RetryableStatusCodes = { StatusCode.Unavailable, StatusCode.ResourceExhausted }
                }
            }
        }
    });
  • ⚠️ Важливо: стандартних налаштувань достатньо для більшості сценаріїв — кастомізація (1.3–1.6) потрібна лише там, де вимоги сервісу відрізняються.

1.3. Кастомізація Retry

Налаштувати поведінку повторних спроб під конкретні вимоги:

  • MaxRetryAttempts — кількість повторів (рекомендовано 2–5);
  • Delay — базова затримка (за замовчуванням 2 с);
  • BackoffType — Exponential (за замовчуванням), Linear або Constant;
  • UseJitter = true — випадкове зміщення затримок, щоб клієнти не повторювали запити одночасно (thundering herd);
  • ShouldHandle — які відповіді та винятки вважати тимчасовими;
  • ⚠️ Важливо: повторювати можна лише ідемпотентні операції. Для POST/PUT/DELETE повтори варто вимкнути — Retry.DisableForUnsafeHttpMethods() — інакше повторний запит може, наприклад, створити замовлення двічі.

CSHARP

builder.Services.AddHttpClient<ReviewsClient>(c => c.BaseAddress = new("https+http://reviews-api"))
    .RemoveAllResilienceHandlers()
    .AddStandardResilienceHandler(o =>
    {
        o.Retry.MaxRetryAttempts = 3;
        o.Retry.Delay = TimeSpan.FromSeconds(1);
        o.Retry.BackoffType = DelayBackoffType.Exponential;
        o.Retry.UseJitter = true;
        o.Retry.DisableForUnsafeHttpMethods();
    });

1.4. Circuit Breaker

Налаштувати «запобіжник», який тимчасово припиняє виклики сервісу, що систематично відмовляє:

  • FailureRatio — частка збоїв, що розмикає ланцюг (за замовчуванням 0.1 = 10 %);
  • MinimumThroughput — мінімальна кількість запитів у вікні для обчислення частки (за замовчуванням 100; для навчального стенду з малим трафіком зменшіть, інакше circuit breaker не спрацює);
  • SamplingDuration — вікно, у якому рахується частка збоїв (30 с);
  • BreakDuration — скільки ланцюг лишається розімкненим перед пробним запитом (5 с);
  • ShouldHandle — які збої враховуються; OnOpened / OnClosed / OnHalfOpened — логування переходів між станами;
  • ⚠️ Важливо: параметри circuit breaker підбираються окремо для кожного сервісу відповідно до його SLA. SamplingDuration має бути щонайменше вдвічі більшим за таймаут спроби — інакше застосунок не запуститься з помилкою валідації налаштувань.

CSHARP

o.CircuitBreaker.FailureRatio = 0.5;
o.CircuitBreaker.MinimumThroughput = 10;          // навчальний стенд: мало запитів
o.CircuitBreaker.SamplingDuration = TimeSpan.FromSeconds(30);
o.CircuitBreaker.BreakDuration = TimeSpan.FromSeconds(15);
o.CircuitBreaker.OnOpened = args =>
{
    logger.LogError("Circuit opened for {Duration}", args.BreakDuration);
    return ValueTask.CompletedTask;
};

Рис. 1. Три стани circuit breaker: Closed — запити проходять; Open — запити одразу відхиляються без виклику сервісу; Half-Open — пропускається пробний запит, від результату якого залежить повернення в Closed або знову в Open.

1.5. Таймаути

Обмежити максимальний час очікування викликів:

  • TotalRequestTimeout — загальний час разом з усіма повторами (30 с);
  • AttemptTimeout — час однієї спроби (10 с);
  • для швидких read-операцій таймаути можна зменшити, для повільних write — збільшити;
  • ⚠️ Важливо: загальний таймаут має враховувати повтори: приблизно таймаут спроби × кількість спроб + затримки між ними. Якщо загальний таймаут менший, повтори просто не встигнуть виконатися.

CSHARP

o.AttemptTimeout.Timeout = TimeSpan.FromSeconds(3);
o.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(15);

1.6. Різні політики для різних сервісів

Підібрати політики resilience відповідно до критичності кожного сервісу:

  • критичні сервіси — більше повторів, чутливіший circuit breaker (у платформі — Каталог: без товарів картку замовлення не зібрати; у загальному випадку — платежі);
  • некритичні сервіси — менше повторів, вища толерантність до збоїв, коротші таймаути (у платформі — Відгуки: Aggregator і без них поверне часткову відповідь, Лаб. 05; у загальному випадку — сповіщення);
  • read-операції — більше повторів (ідемпотентні); write — менше, щоб уникнути дублювання змін;
  • для повністю власного набору стратегій — AddResilienceHandler("назва", builder => ...);
  • ⚠️ Важливо: задокументуйте, чому для кожного клієнта обрано саме такі значення.

CSHARP

// Критичний: Каталог
builder.Services.AddHttpClient<CatalogClient>(c => c.BaseAddress = new("https+http://catalog-api"))
    .RemoveAllResilienceHandlers()
    .AddStandardResilienceHandler(o =>
    {
        o.Retry.MaxRetryAttempts = 5;
        o.CircuitBreaker.FailureRatio = 0.3;          // чутливіший
    });
// Некритичний: Відгуки — швидко здатися і повернути часткову відповідь
builder.Services.AddHttpClient<ReviewsClient>(c => c.BaseAddress = new("https+http://reviews-api"))
    .RemoveAllResilienceHandlers()
    .AddStandardResilienceHandler(o =>
    {
        o.Retry.MaxRetryAttempts = 1;
        o.AttemptTimeout.Timeout = TimeSpan.FromSeconds(2);
        o.TotalRequestTimeout.Timeout = TimeSpan.FromSeconds(5);
        o.CircuitBreaker.FailureRatio = 0.7;          // менш чутливий
    });

1.7. Resilience для Redis

Налаштувати відмовостійкість розподіленого кешу з Лаб. 06:

  • Aspire-інтеграція Redis уже керує повторним підключенням ConnectionMultiplexer;
  • реалізувати graceful degradation: якщо Redis недоступний, сервіс працює без кешу, звертаючись до бази даних;
  • операції з кешем — у try/catch; збій кешу логується, але не провалює запит;
  • ⚠️ Важливо: кеш — необов’язкова залежність, а не частина критичного шляху. Той самий принцип відображає health check Redis зі статусом Degraded (Частина 3.3).

CSHARP

// у GetOrCreateAsync з Лаб. 06, Частина 3.3
byte[]? bytes = null;
try
{
    bytes = await _redis.GetAsync(key, ct);
}
catch (Exception ex) when (ex is RedisConnectionException or RedisTimeoutException)
{
    _logger.LogWarning(ex, "Redis unavailable, falling back to database for {Key}", key);
}
// ... читання з БД ...
try { await _redis.SetAsync(key, payload, options, ct); }
catch (Exception ex) when (ex is RedisConnectionException or RedisTimeoutException)
{
    _logger.LogWarning(ex, "Redis unavailable, value for {Key} not cached", key);
}

1.8. Метрики resilience в Aspire Dashboard

Використати вбудовану телеметрію для аналізу поведінки resilience:

  • Polly публікує метрики через Meter з назвою Polly — додайте його в ServiceDefaults: .WithMetrics(m => m.AddMeter("Polly"));
  • resilience.polly.strategy.events — лічильник подій; тег event.name показує тип події: OnRetry, OnCircuitOpened, OnCircuitHalfOpened, OnCircuitClosed, OnTimeout;
  • resilience.polly.strategy.attempt.duration — тривалість кожної спроби (тег attempt.number);
  • resilience.polly.pipeline.duration — тривалість усього виклику разом із повторами;
  • http.client.request.duration — затримка HTTP-викликів з урахуванням resilience;
  • фільтрувати метрики за pipeline.name — окремо для кожного клієнта;
  • ⚠️ Важливо: велика кількість повторів або часте розмикання ланцюга сигналізують про проблему в сервісі, до якого звертаються, — це привід для розслідування, а не доказ, що «resilience спрацювала».

1.9. Логування resilience-подій

Переглянути, як resilience-події потрапляють у логи:

  • кожен повтор логується з рівнем Warning (номер спроби, затримка, причина);
  • розмикання ланцюга — Error, повернення в Closed — Information; таймаути — Error;
  • записи містять властивості ServiceName, CorrelationId, TraceId (Лаб. 05);
  • у Structured logs Dashboard — фільтр за категорією Polly;
  • ⚠️ Важливо: логи resilience допомагають побачити закономірності збоїв і підібрати налаштування політик.

1.10. Тестування resilience

Перевірити ефективність механізмів resilience на сценаріях збоїв:

  • тимчасовий збій: зупинити сервіс Відгуків на 5–10 с з Dashboard і перевірити повтори;
  • circuit breaker: створити постійні збої та переконатися, що ланцюг розмикається і запити відхиляються миттєво;
  • таймаути: додати штучну затримку в сервіс (наприклад, await Task.Delay у тестовому ендпоінті);
  • спостерігати за Dashboard у реальному часі та перевіряти логи;
  • виміряти, яку додаткову затримку вносять самі повтори;
  • ⚠️ Важливо: resilience має підвищувати доступність без суттєвої втрати продуктивності.
  • Контрольна точка: зупиніть reviews-api з Dashboard на 5–10 с — у логах видно повтори, а Aggregator швидко повертає часткову відповідь; серія збоїв розмикає ланцюг (OnCircuitOpened), і запити відхиляються без очікування таймауту.

Частина 2. Впровадження Custom Business Metrics (обов’язково)

Створити метрики для моніторингу бізнес-логіки через OpenTelemetry Meter API (System.Diagnostics.Metrics).

2.1. Meter

Створити Meter у кожному мікросервісі:

  • Meter створюється через IMeterFactory з DI (як CacheMetrics у Лаб. 06) в окремому класі метрик;
  • назва Meter відповідає сервісу — Orders.Api, Catalog.Api — для коректної атрибуції;
  • Meter додається в конфігурацію OpenTelemetry (AddMeter) в ServiceDefaults; експорт в Dashboard по OTLP уже налаштовано;
  • ⚠️ Важливо: клас метрик реєструється як Singleton і живе протягом усього часу роботи застосунку.

2.2. Бізнес-лічильники

Визначити лічильники для критичних бізнес-операцій кожного сервісу:

  • Counter<long> — через meter.CreateCounter<long>(name, unit, description);
  • виміри (теги) для фільтрації: статус замовлення, тип користувача, спосіб оплати, результат операції;
  • лічильник збільшується одразу після успішної операції;
  • назви з префіксом простору імен: orders.created, orders.confirmed, products.updated;
  • ⚠️ Важливо: лічильник лише зростає; для поточного стану використовується gauge (Частина 2.4).

CSHARP

public class OrderMetrics
{
    private readonly Counter<long> _ordersCreated;
    private readonly Histogram<double> _operationDuration;
    public OrderMetrics(IMeterFactory meterFactory)
    {
        var meter = meterFactory.Create("Orders.Api");
        _ordersCreated = meter.CreateCounter<long>(
            "orders.created", unit: "{order}", description: "Number of created orders");
        _operationDuration = meter.CreateHistogram<double>(
            "orders.operation.duration", unit: "ms", description: "Duration of order operations");
    }
    public void OrderCreated(string status) =>
        _ordersCreated.Add(1, new KeyValuePair<string, object?>("order.status", status));
    public void RecordDuration(string operation, bool success, double ms) =>
        _operationDuration.Record(ms,
            new KeyValuePair<string, object?>("operation", operation),
            new KeyValuePair<string, object?>("status", success ? "success" : "failure"));
}
// Program.cs сервісу замовлень
builder.Services.AddSingleton<OrderMetrics>();
// ServiceDefaults: .WithMetrics(m => m.AddMeter("Orders.Api", "Catalog.Api", "Catalog.Cache", "Polly"))

2.3. Вимірювання затримки

Створити гістограми для детального аналізу продуктивності критичних операцій:

  • Histogram<double> — через meter.CreateHistogram<double>(name, unit);
  • Stopwatch для точного вимірювання; значення — у мілісекундах для узгодженості;
  • виміри: тип операції, успіх/помилка, попадання в кеш, тип запиту до БД;
  • межі кошиків гістограми за потреби задаються через OpenTelemetry View (ExplicitBucketHistogramConfiguration);
  • ⚠️ Важливо: тривалість записується для ВСІХ виконань, включно з невдалими — інакше картина продуктивності викривлена.

CSHARP

var sw = Stopwatch.StartNew();
try
{
    await _orderService.ConfirmOrderAsync(orderId, ct);        // Лаб. 02
    _metrics.RecordDuration("confirm", success: true, sw.Elapsed.TotalMilliseconds);
}
catch
{
    _metrics.RecordDuration("confirm", success: false, sw.Elapsed.TotalMilliseconds);
    throw;
}

2.4. Gauge-метрики

Створити gauge для моніторингу поточного стану:

  • ObservableGauge — кількість активних з’єднань, розмір кешу, глибина черги (черги з’являться в Лаб. 08);
  • значення читається callback-функцією в момент збирання метрик;
  • ⚠️ Важливо: gauge показує знімок поточного стану, а лічильник накопичує значення.

CSHARP

meter.CreateObservableGauge("orders.awaiting_validation",
    () => _ordersSnapshot.CountAwaitingValidation,               // значення на момент збору
    unit: "{order}", description: "Orders waiting for stock confirmation");

2.5. Виміри та кардинальність

Визначити, за якими тегами фільтруватимуться метрики:

  • теги, корисні для пошуку проблем: назва сервісу, ендпоінт, код статусу, результат операції;
  • уникати тегів з великою кількістю унікальних значень: ідентифікатори користувачів, часові мітки, ідентифікатори запитів;
  • однакові назви тегів в усіх сервісах; значення кожного тегу задокументувати;
  • ⚠️ Важливо: кожна унікальна комбінація значень тегів — окремий часовий ряд; тег з ідентифікатором користувача може створити мільйони рядів і перевантажити систему метрик.

2.6. Перевірка збору метрик

Переконатися, що метрики збираються й експортуються:

  • виконати запити, що змінюють метрики (створити кілька замовлень);
  • відкрити вкладку Metrics в Aspire Dashboard і знайти свої інструменти;
  • перевірити, що теги передаються й за ними можна фільтрувати;
  • ⚠️ Важливо: метрики з’являються в Dashboard за кілька секунд. Якщо метрики немає — перевірте, чи додано Meter через AddMeter.
  • Контрольна точка: створіть кілька замовлень — у вкладці Metrics видно orders.created з фільтром за order.status і розподіл orders.operation.duration.

Частина 3. Налаштування Comprehensive Health Checks (обов’язково)

Реалізувати health check endpoints для моніторингу стану всіх інфраструктурних компонентів.

3.1. NuGet-пакети

Додати пакети для health checks:

Пакет Призначення
Microsoft.Extensions.Diagnostics.HealthChecks базова функціональність (вже в ASP.NET Core)
AspNetCore.HealthChecks.SqlServer стан SQL Server (Замовлення, Каталог)
AspNetCore.HealthChecks.MongoDb стан MongoDB (Відгуки)
AspNetCore.HealthChecks.Redis стан Redis (кеш)
AspNetCore.HealthChecks.Uris доступність довільних HTTP-ендпоінтів
Grpc.AspNetCore.HealthChecks, Grpc.HealthCheck стандартний gRPC-протокол перевірки стану (сервер і клієнт)

Таблиця 3. Пакети для health checks.

Клієнтські інтеграції Aspire (AddSqlServerDbContext, AddMongoDBClient, AddRedisDistributedCache) реєструють health check своєї бази автоматично. Явна реєстрація нижче потрібна, щоб задати назву, теги й статус збою.

3.2. Health checks баз даних

Додати перевірки SQL Server і MongoDB у відповідні мікросервіси:

  • SQL Server — AddSqlServer(...), MongoDB — AddMongoDb(...);
  • зрозумілі назви (orders-db, reviews-db) для швидкої ідентифікації в Dashboard;
  • таймаут 5–10 с;
  • теги для категоризації: "database", "ready" (для readiness-перевірки);
  • перевірка виконує найпростіший запит: SQL Server — SELECT 1, MongoDB — ping;
  • ⚠️ Важливо: health check має бути легким — він виконується регулярно, тож важкі запити до БД неприпустимі.

CSHARP

// сервіс замовлень (Лаб. 02)
builder.Services.AddHealthChecks()
    .AddSqlServer(
        connectionString: builder.Configuration.GetConnectionString("OrdersDb")!,
        name: "orders-db",
        failureStatus: HealthStatus.Unhealthy,
        tags: ["database", "sql", "ready"],
        timeout: TimeSpan.FromSeconds(5));
// сервіс відгуків (Лаб. 04) — перевірка через зареєстрований IMongoClient
builder.Services.AddHealthChecks()
    .AddMongoDb(
        sp => sp.GetRequiredService<IMongoClient>(),
        name: "reviews-db",
        failureStatus: HealthStatus.Unhealthy,
        tags: ["database", "mongodb", "ready"],
        timeout: TimeSpan.FromSeconds(5));

Сигнатури методів розширення відрізняються між версіями пакетів AspNetCore.HealthChecks.* — звіряйтеся з README репозиторію Xabaril для встановленої версії.

3.3. Health check Redis

Додати перевірку доступності розподіленого кешу:

  • AddRedis(...) надсилає команду PING;
  • таймаут 3–5 с — кеш має бути швидким;
  • статус збою Degraded, а не Unhealthy, бо кеш — необов’язкова залежність (Частина 1.7);
  • ⚠️ Важливо: якщо сервіс працює без кешу, недоступність Redis не повинна робити весь сервіс Unhealthy.

CSHARP

.AddRedis(
    redisConnectionString: builder.Configuration.GetConnectionString("redis")!,
    name: "redis-cache",
    failureStatus: HealthStatus.Degraded,        // кеш необов’язковий
    tags: ["cache", "redis"],
    timeout: TimeSpan.FromSeconds(3));

3.4. Health checks gRPC-сервісів

Перевіряти доступність сервісів, від яких залежить Aggregator:

  • у кожному gRPC-сервісі (Лаб. 06) увімкнути стандартний gRPC Health Checking Protocol — AddGrpcHealthChecks() і MapGrpcHealthChecksService(); він відповідає на основі тих самих health checks ASP.NET Core;
  • в Aggregator створити власний IHealthCheck, що викликає метод Check стандартного клієнта Health;
  • короткий таймаут (2–3 с) для швидкого виявлення недоступності;
  • RpcException перетворюється на Unhealthy, збій логується;
  • ⚠️ Важливо: health check ідемпотентний і не має побічних ефектів у сервісі, який перевіряє.

CSHARP

// у сервісі Каталогу
builder.Services.AddGrpcHealthChecks();
app.MapGrpcHealthChecksService();
// в Aggregator
public class CatalogHealthCheck(Health.HealthClient client, ILogger<CatalogHealthCheck> logger) : IHealthCheck
{
    public async Task<HealthCheckResult> CheckHealthAsync(
        HealthCheckContext context, CancellationToken ct = default)
    {
        try
        {
            var reply = await client.CheckAsync(new HealthCheckRequest(),
                deadline: DateTime.UtcNow.AddSeconds(2), cancellationToken: ct);
            return reply.Status == HealthCheckResponse.Types.ServingStatus.Serving
                ? HealthCheckResult.Healthy("catalog-api is serving")
                : HealthCheckResult.Unhealthy($"catalog-api status: {reply.Status}");
        }
        catch (RpcException ex)
        {
            logger.LogWarning(ex, "catalog-api health check failed");
            return HealthCheckResult.Unhealthy("catalog-api is unavailable", ex);
        }
    }
}
builder.Services.AddGrpcClient<Health.HealthClient>(o => o.Address = new Uri("https://catalog-api"));
builder.Services.AddHealthChecks()
    .AddCheck<CatalogHealthCheck>("catalog-api", tags: ["grpc", "downstream", "ready"]);

3.5. Liveness, readiness та startup

Створити окремі endpoints для різних сценаріїв оркестрації:

  • liveness (/health/live) — чи живий процес; без перевірки зовнішніх залежностей;
  • readiness (/health/ready) — чи готовий сервіс приймати трафік (усі залежності доступні);
  • startup (/health/startup) — для сервісів із повільним стартом;
  • розподіл перевірок між endpoints — за тегами через Predicate у MapHealthChecks;
  • ⚠️ Важливо: liveness має бути надшвидким (< 100 мс), readiness може бути ґрунтовнішим (до кількох секунд). Шаблон ServiceDefaults вже додає перевірку "self" з тегом "live" і endpoint /alive — його можна використати як liveness.

CSHARP

// після builder.Build()
app.MapHealthChecks("/health/live", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("live")
});
app.MapHealthChecks("/health/ready", new HealthCheckOptions
{
    Predicate = check => check.Tags.Contains("ready"),
    ResponseWriter = WriteJsonResponse          // деталі кожної перевірки у JSON
});

Рис. 2. Liveness (/health/live) перевіряє лише сам процес, readiness (/health/ready) — реальні залежності. Оркестратор реагує по-різному: збій liveness — перезапуск процесу, збій readiness — тимчасове виключення з балансування.

3.6. Інтеграція з Aspire Dashboard

Показувати стан сервісів у Dashboard:

  • у AppHost для кожного сервісу вказати endpoint перевірки — WithHttpHealthCheck("/health"); тоді Dashboard показує стан ресурсу (Healthy / Degraded / Unhealthy), а WaitFor чекає, поки залежність стане здоровою, а не лише запуститься;
  • MapDefaultEndpoints() з ServiceDefaults публікує /health і /alive; з міркувань безпеки шаблон робить це лише в середовищі Development;
  • порядок реєстрації health checks відносно AddServiceDefaults() не важливий — вони накопичуються в одній колекції;
  • деталі окремих перевірок — у вкладці Resources (клік на ресурс) та в логах категорії HealthChecks.

CSHARP

// Program.cs AppHost
var orders = builder.AddProject<Projects.Orders_Api>("orders-api")
    .WithReference(ordersDb).WaitFor(ordersDb)
    .WithHttpHealthCheck("/health");
var aggregator = builder.AddProject<Projects.Platform_Aggregator>("aggregator")
    .WithReference(orders).WaitFor(orders)            // тепер чекає Healthy
    .WithHttpHealthCheck("/health");
  • Контрольна точка: зупиніть SQL Server — /health/live відповідає 200, а /health/ready — ні; зупиніть Redis — /health/ready показує Degraded.

Частина 4. Візуалізація метрик та моніторинг у Aspire Dashboard (обов’язково)

Використати Aspire Dashboard для спостереження за всією системою і роботи з отриманими метриками.

4.1. Structured logs

Проаналізувати логи всіх сервісів:

  • фільтрувати за назвою сервісу та рівнем (errors, warnings);
  • шукати за CorrelationId для наскрізного відстеження запиту;
  • аналізувати структуровані властивості та обмежувати часовий діапазон для конкретних інцидентів;
  • ⚠️ Важливо: структуровані логи дають змогу шукати за значенням конкретної властивості, а не лише за текстом.

4.2. Traces

Проаналізувати розподілене трасування:

  • знайти trace за TraceId; переглянути ієрархію Gateway → Aggregator → мікросервіси → бази даних;
  • тривалість кожного span — для пошуку вузьких місць; spans з помилками — для аналізу збоїв;
  • паралельні та послідовні виклики; повторні спроби видно як кілька spans одного виклику;
  • порівняти тривалість trace до і після впровадження resilience;
  • ⚠️ Важливо: traces показують реальний шлях запиту через розподілену систему.

4.3. Metrics

Візуалізувати бізнес- і технічні метрики:

  • знайти власні лічильники за назвою Meter (Orders.Api, Catalog.Cache);
  • тренди бізнес-операцій: замовлення за хвилину, частка попадань у кеш;
  • розподіли гістограм затримок; порівняння між сервісами;
  • часовий діапазон та фільтри за тегами;
  • ⚠️ Важливо: агрегація метрик залежить від обраного часового вікна.

4.4. Resources

Переглянути загальний стан системи:

  • усі сервіси й контейнери з кольоровим статусом: зелений — Healthy, жовтий — Degraded, червоний — Unhealthy;
  • використання CPU і пам’яті; кількість перезапусків — для виявлення нестабільних сервісів;
  • деталі health checks — по кліку на ресурс;
  • ⚠️ Важливо: Resources — головна панель операційного моніторингу.

4.5. Ефективність resilience

Оцінити, як resilience вплинула на систему:

  • порівняти частку помилок до і після налаштування політик;
  • частку успішних повторів — за resilience.polly.strategy.events з event.name = OnRetry;
  • переходи circuit breaker — у логах і в метриці з OnCircuitOpened / OnCircuitClosed;
  • зміну доступності за health checks; розподіли затримок;
  • ⚠️ Важливо: метрики мають показати зменшення кількості невдалих запитів.

4.6. Налаштування моніторингу

Підготувати Dashboard до постійного моніторингу:

  • задокументувати, які метрики критичні для бізнесу, і їхні нормальні діапазони;
  • підготувати типові фільтри для пошуку проблем;
  • ⚠️ Важливо: Aspire Dashboard — інструмент розробки; у production використовуються спеціалізовані системи (Grafana, Prometheus, Azure Monitor / Application Insights).
  • Контрольна точка: метрика resilience.polly.strategy.events з фільтром event.name показує OnRetry і OnCircuitOpened під час тестових збоїв.

Критерії приймання

  • Standard Resilience Handler діє для всіх HTTP- та gRPC-клієнтів без нашарування обробників.
  • Для gRPC-клієнтів налаштовано retry-політику за gRPC-статусами.
  • Політики retry, circuit breaker і таймаути кастомізовані відповідно до критичності сервісів.
  • Кешування Redis має graceful degradation із запасним читанням з бази даних.
  • Створено власні бізнес-лічильники, гістограми затримок і gauge-метрики через Meter API.
  • Health checks налаштовано для SQL Server, MongoDB, Redis (Degraded) і gRPC-залежностей.
  • Liveness і readiness розділені; відповіді містять деталі кожної перевірки.
  • Aspire Dashboard показує стан усіх ресурсів (WithHttpHealthCheck).
  • Логи, traces і метрики доступні й фільтруються в Dashboard.
  • Ефективність resilience підтверджена метриками; переходи circuit breaker видно в логах.
  • Система демонструє graceful degradation при часткових збоях замість каскадних відмов.

Перед здачею перевірте себе:

  • зупиніть reviews-api — Aggregator швидко повертає часткову відповідь, а в метриках видно OnRetry;
  • створіть серію збоїв — ланцюг розмикається (OnCircuitOpened), запити відхиляються без очікування таймауту; після BreakDuration ланцюг повертається в Closed;
  • зупиніть Redis — /health/ready показує Degraded, а сервіс продовжує відповідати;
  • зупиніть SQL Server — /health/live відповідає 200, а /health/ready — ні;
  • створіть кілька замовлень — orders.created зростає, orders.operation.duration показує розподіл.
